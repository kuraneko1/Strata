# Running Strata on Tesla V100 (sm_70)

**Status:** community patch, not part of upstream. Branch `v100-port`, based on `v0.2.1.4`.
Upstream keeps changing; expect to re-port on every update.

## What it fixes

`Qwen3.8-Flash-Next` GGUFs carry the MTP (NextN) block as a 49th layer: `block_count = 49 = 48` trunk `+ 1`.
Upstream reads `qwen4exp.block_count` straight into `n_layers` and requires `attention.compress_ratios` to hold
exactly that many entries, so such a file is refused. It also subtracts `nextn_predict_layers` only for
`qwen35moe`. This branch:

- `include/strata/artifact/gguf_reader.hpp` - subtract `nextn_predict_layers` from `block_count` (the kernels and the
  pack describe the trunk); a `compress_ratios` array that is longer than the trunk, or that disagrees with
  `full_attention_interval`, is reported once and ignored (the compiled pooling block is used).
- `include/strata/core/family_layout.hpp` - read `nextn_predict_layers` for Flash-Next as well and subtract it;
  `n_mtp_layers` stays 0.
- `src/core/native_dense.cpp` - skip tensors of blocks past the last one the pack describes: the in-file MTP block
  is served from `--mtp`.

`patches/v100-in-file-mtp.patch` is the same change as a standalone patch.

## Build

CUDA 13 no longer compiles `sm_70`; use CUDA 12.9 with `STRATA_EXPERIMENTAL_SM60=ON`.

```sh
cmake -S . -B build-cuda12 -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DSTRATA_ENABLE_CUDA=ON -DSTRATA_BUILD_TESTS=OFF \
  -DSTRATA_Q6K_EXPERTS=ON -DSTRATA_MMQ_KQUANTS=ON \
  -DCMAKE_CUDA_ARCHITECTURES='70' \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.9/bin/nvcc -DCUDAToolkit_ROOT=/usr/local/cuda-12.9 \
  -DSTRATA_GGML_DIR="$PWD/third_party/llama.cpp" -DSTRATA_EXPERIMENTAL_SM60=ON
cmake --build build-cuda12 --target strata -j"$(nproc)"
```

For a mixed **V100 + RTX 3090** host build both architectures into one binary:

```sh
  -DCMAKE_CUDA_ARCHITECTURES='70;86'
```

## Tested on

`Qwen3.8-Flash-Next` IQ3E + Q8D pack (80 GiB GGUF, in-file MTP), CUDA 12.9, driver 580.178.04.

| Host | Config | Result |
|---|---|---|
| 2x V100 32GB | `gpu:[0,1]`, 262k ctx, KV q8 | works, ~86-96 tok/s decode in short chats |
| V100 + RTX 3090 | `gpu:[0,1]`, `gpu_order:as_given`, 65k/262k, KV int8, `--mmap-experts` | works; ~109-124 tok/s prefill, 48-77 tok/s decode on long prompts |
| RTX 3090 only | `gpu:[1]`, 262k, KV int8, `--mmap-experts --ple-io ram` | works; 22.8 GiB VRAM, 45 s start |

Numbers are from one machine and differ with the prompt, the expert cache and the page cache; treat them as
orders of magnitude, not as a benchmark.

## Known limits

- One `Xid 43` and `dequant launch: unspecified launch failure` happened once on the RTX 3090 during a 22.5k-token
  prompt with a binary built for `sm_70` only. It did not reproduce after rebuilding for `70;86` and raising the
  VRAM reserves; the cause was never isolated.
- `--kv-streaming` and long contexts on 24 GB cards are sensitive to the VRAM reserve (`--vram-reserve-mib`,
  `--vram-reserve-later-mib`).
- `--ple-io ram` needs `LimitMEMLOCK` high enough to lock the ~28.8 GB table, otherwise the engine logs
  `PLE table mlock failed` and the pages can be reclaimed.
- The V100 has no bf16 tensor cores; expect the GPU-side expert work to differ from Ampere cards.
